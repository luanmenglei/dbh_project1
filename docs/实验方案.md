# 课程电影数据的 DBMS 性能评估方案

## 研究目标

1. 直接文件操作与 DBMS 在扫描、索引、关联、聚合和持久化更新中的性能边界是什么？
2. 相同 CPU、内存和存储预算下，PostgreSQL 与 openGauss 的并发吞吐、延迟和资源使用如何变化？
3. 观察到的差异能否由执行计划、索引、结果传输、事务日志和缓存状态解释？

不预设数据库一定比文件快，不依据单一查询宣称某个产品总体更好。本项目不实现自己的完整数据库系统。

## 数据与模式

课程原始 SQL SHA-256 由每个数据目录清单记录。原始规模：185 个国家、9,204 部电影、16,489 个人物、46,850 条演职关联。其他名称和论坛表不进入实验。

只解析这四张表的 INSERT 字面量，避免原脚本混用 PRAGMA 和 E 字符串语法的导入问题。原 SQL 保持不变，目标 DDL 显式指定字段、主外键和唯一约束。`char` 改为有同样长度上限的 `varchar`，避免定长补空格影响跨系统结果校验。性别与角色值原样保留，不猜测未说明的业务含义。

规模档位 s1、s10、s100。电影与人物 ID 按原最大 ID + 1 偏移，关联同步映射，国家表不复制。新增 replica 字段将原有业务唯一约束限定在每个副本内。原始标题、姓名、年份、片长及其 NULL 保持不变，不通过添加标题后缀改变匹配率。

这是重复结构的扩展数据，不代表新增真实电影。副本提高规模，但不同副本高度相关；报告必须将这一点作为外部有效性限制。相同人物 ID 的关联查询仍只返回该副本的关联，不会随着副本数增加而自动增加返回行数；此实验测量相同结果规模下的查找成本。

## 实验矩阵

| 组 | 操作 | 数据规模 | 主要指标 |
|---|---|---|---|
| A1 | 标题包含 The/Love/Star，只返回计数 | 1/10/100 | 端到端时间、匹配正确性 |
| A2 | 同条件返回 movieid/title 全部结果 | 1/10/100 | 包含传输与消费的时间 |
| B | 均匀随机 movieid 查询，100 次/轮 | 1/10/100 | 平均耗时、分位延迟、文件索引构建/加载成本 |
| C | 名和姓中的 T 全部替换成 Ttt | 1/10/100 | 含提交/同步的时间、受影响行数、大小变化 |
| D1 | 给定 peopleid，关联查询电影及角色 | 1/10/100 | 时间、结果指纹、执行计划 |
| D2 | 按国家和年份聚合片长 | 1/10/100 | 时间、分组结果正确性 |
| E | 并发随机主键只读 | 1/100 | 吞吐、P50/P95/P99、资源计数器 |
| F | 90% 主键读取 + 10% 单行片长更新 | 1/100 | 吞吐、读/写各自 P95、错误率 |

串行操作每配置 5 轮；并发 1/2/4/8/16/32 客户端，每次共同预热 30 秒后测量 120 秒，3 轮。客户端是闭环负载：一个请求完成才发下一个，没有外部固定到达率。结论不得当作开放到达模型下的排队延迟预测。

## 查询与实现口径

标题查询使用 `strpos(title, $1)>0`，明确为区分大小写的字面子串，与 C++ 字符串查找一致；不把 `%`、`_` 当作通配符。A1 两边都只返回一个计数，A2 两边都消费全部同样字段，不打印到终端。普通 B-tree 对这种任意位置子串的索引收益不作为假设；诊断执行计划保存实际访问方式。两个 DB 均不安装额外文本索引插件。

B 对比 C++ 顺序扫描、C++ 文件偏移索引、数据库主键索引。顺序扫描找到唯一 ID 后停止。文件索引包含 ID 和偏移，进入进程后装入哈希表；电影正文仍从文件读取。索引建立耗时与磁盘字节数单独记录；读取索引、ID 列表和建立连接属于 setup_s，不计入稳态请求延迟。文件偏移索引受文件大小及修改时间保护，数据改变后必须重建。三个实现使用同一 C++ 随机发生器与同样的 ID 列表、请求数、种子。

D1 文件实现先扫描 credits，建立选中电影 ID 的哈希映射，再扫描 movies。映射构建计入查询；数据库具有 credits(peopleid,movieid) 索引。该比较衡量“单次临时文件处理 vs 持久索引数据库”的实际方案差异，不将全部收益归因于数据库引擎。文件永久关联索引属于可选扩展，不在核心实现范围内。

D2 返回 country、year_released、count(*)、sum(runtime)、count(runtime)。通过整数总和和非空计数比较，避免浮点平均值舍入差异；平均片长由 sum/count 得到，count 为零时为 NULL。

C 文件采用读取、写临时文件、fsync 临时文件、原子替换、fsync 父目录；DB 包含 BEGIN、UPDATE、COMMIT，并要求 fsync 和同步提交开启。这是相近的“返回前请求持久化”边界，不等价于已证明相同的故障恢复能力，也没有模拟断电。文件大小与数据库关系/索引占用只是逻辑空间指标，不是设备真实写入量。

每次 C 从原姓名恢复；T → Ttt 不是幂等操作，绝不在上轮结果上重测。DB 恢复通过独立 schema 重建导入，文件恢复通过原始副本复制。恢复与查询预热单独记录，不加入更新计时。

F 只更新 runtime，保留姓名更新的独立性。每条写入是一条自动提交 UPDATE，值在 1..300 间循环，NULL 变为 1。每轮并发测试都重新导入，避免前轮更新和表膨胀影响下一轮。多个客户端可命中同一行，行锁成本属于混合负载；不提供自动重试掩盖错误。

## 计时与正确性

主计时器为 C++ steady_clock，单次查询计时包括服务端处理、返回结果和客户端指纹计算。连接、prepare、索引装载不计入请求时间但单独报告 setup_s；正式 DB 会话通过 libpq 持久连接与参数化 prepared statements 执行。文件与 DB 的每个输出行均经过同一校验过程。

并发客户端全部连接和 prepare 完成后统一启动。共同预热结束后，按请求开始时刻纳入测量；边界之前开始的请求不计入。测量结束后等待已经开始的请求完成，吞吐分母包含最后请求的排空时间。P50/P95/P99 使用桶宽约 1% 的有界内存几何直方图，单位毫秒，不伪装成无误差的精确排序分位数。任何连接、SQL 或结果行数错误都让整轮无效，并使实验停止。

逐表行数与无序内容指纹验证导入；所有串行查询与文件参考结果比较。指纹用带 NULL 标记和长度边界的逐行 FNV-1a，再对行哈希做模 2^64 加和；能检测常见差错，但不是密码学无碰撞证明。输入文件本身用 SHA-256 校验。测试另用独立 Python 实现覆盖特殊字符、NULL、多角色关联、全 NULL 聚合、缺失关键词、更新、恢复和过期索引。

## 服务器控制

数据库容器使用相同的 CPU 集、NUMA 内存节点、内存上限、shared_buffers=512MB、work_mem=4MB、max_connections=128。主实验关闭单条查询内部并行（PostgreSQL max_parallel_workers_per_gather=0；openGauss query_dop=1），让 E/F 聚焦多会话扩展性。DB 其他默认参数可能不同，完整 pg_settings 会保存；不声称两个产品所有内部机制一一相同。

默认仅在一个数据库运行时测它，轮次交替后端顺序。客户端另分配 CPU，监测是否成为瓶颈；文件基线记录同样的硬件范围和实际内存用量。C++ 文件程序本身不由部署脚本自动施加数据库容器的内存限制，所以超内存压力实验不应直接据此比较文件与 DB。若要做这种实验，需再给文件程序设置等价的 cgroup 限额并明确 OS 缓存归属。

主实验是操作性定义的预热状态：串行每轮同查询先跑一次，并发有固定预热窗口。数据超出内存时不承诺全部驻留内存。当前代码不清系统缓存、不自动运行冷缓存实验，不把“重启数据库”标记为冷缓存。保留操作系统及 DB 的正常检查点和维护机制，记录配置及异常，不挑选最好的一次。

## 执行验收

- 本地：独立测试通过，临时 PostgreSQL 与 C++ 结果一致。
- 服务器冒烟：两个数据库均成功部署，原始数据导入一致，各查询、更新和并发无错误。
- 正式：完整输出目录有 COMPLETE、无 FAILED，记录足够重复轮次与完整版本信息。
- 报告：只使用服务器正式结果，不填入预测数字；解释偏差与失败，不删除不利结果。
