扩展性追查：实验协议与解释边界
2026-10-13，北京时间

问题：原 compact 结果中，openGauss 随 1/4/8 客户端近线性增长，而 PostgreSQL 起点更高、随后放缓。区分数据库饱和与发压客户端饱和。

授权与资源：用户允许在实时余量充足时放宽原十核限制。两次 30/10 秒读数显示整机 CPU 约 3%，可用内存约 229 GiB；发现原客户端附近 CPU 17 与 CPU 19 的 SMT 兄弟有其他任务活动，因此本轮重新选择较空闲核心。CPU 亲和性不是独占预留。

三种分配（全部位于 NUMA 节点 0；不使用 SMT 兄弟）：
db8_client2：数据库 CPU 8-15；客户端 24,25，总计 10 个物理核。
db8_client4：数据库 CPU 8-15；客户端 24-27，总计 12 个物理核。
db12_client4：数据库 CPU 8-15,20-23；客户端 24-27，总计 16 个物理核。

数据库仍各限内存 8 GiB、无 swap、Nice=10、TasksMax=256；运行器/客户端作用域 4 GiB、TasksMax=128。两库不同时运行。没有全局设置改动，无磁盘限速。主矩阵每轮前检查可用内存、磁盘空间及系统负载；低于 32 GiB 可用内存、低于 40 GiB 磁盘可用空间、1 分钟负载超过 32 时停止并释放服务。这是保守停止条件，并非精确归因给其他任务的负载检测。

主矩阵：
1. db8_client2，纯读客户端 1/4/8/16/32；混合客户端 8/32。
2. db8_client4，纯读客户端 8/32。
3. db12_client4，纯读客户端 8/32。
两库各测、每组 3 轮、预热 5 秒、测量 20 秒，共 66 轮，固定窗口 1650 秒。
每轮恢复 s10 并核对四表指纹；不同轮次打乱资源分配顺序及客户端条件顺序，两库先后交替。

保持不变：原 C++ 二进制、查询、数据规模、结果消费与校验、连接/预编译复用、持久化和数据库配置。query_dop 等参数未调优。本轮不是“各产品最佳调优成绩”。原客户端 CPU 16/17 改为 24/25，所以须用本轮重新测得的基线做干预比较，不能将旧值与新值直接当配对实验。

新增测量：每 0.5 秒采样 /proc/客户端PID/stat 的累计 utime+stime，数据库 cgroup cpu.stat，memory.current、memory.events、io.stat 及主机 CPU。CPU 核用量=CPU 秒增量/墙钟秒增量。分析保守剔除进程启动后 warmup+1 秒以前的样本，使用内部窗口；原 C++ 没有导出精确的测量起点，因此 CPU 与完整吞吐窗口并不完全重合。CPU 微秒/请求是近似量，不是精确的函数级剖析。

判别逻辑：
H1 客户端瓶颈：客户端接近核上限、DB 仍有余量；固定 DB=8 核，把客户端 2→4 核后吞吐显著提高。
H2 数据库侧资源瓶颈：客户端尚有余量，固定客户端=4 核，把 DB 8→12 核后高并发吞吐显著提高。
H3 排队：增加连接不再提高吞吐，而 P95/P99 上升。只说明当前系统/资源组合的饱和，不是数据库的普遍极限。
H4 两边都未跑满：应检查同步往返、调度、锁等待或缓存等；不可仅凭吞吐曲线断言具体内核函数慢。

可能追加的验证：若主矩阵显示稳定的干预效果，可对少量关键条件做分钟级持续复测，以排除短窗口偶然现象；独立输出、单独标记，不混入原三轮中位数。是否追加取决于实际结果和服务器余量。

边界：没有 perf 工具，内核 perf_event_paranoid=4；不修改共享服务器的系统限制。即使识别出发压端/服务端瓶颈，也不能声称已精确定位 openGauss 内核每个函数的成本。对代码路径原因应标为待进一步剖析。
