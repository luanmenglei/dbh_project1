## 实际环境与资源边界

- Ubuntu 22.04.5、双路 AMD EPYC 7542，64 个物理核、128 个逻辑 CPU。
- 所有项目进程由 `ycx` 运行；没有使用 sudo、Docker 或系统级数据库服务。
- 数据库使用逻辑 CPU 8–15，客户端使用 16、17，总计十个不同物理核上的十个逻辑 CPU。没有使用对应 SMT 兄弟线程 72–81。
- 准备、解压、初始化与编译使用 CPU 8、9，nice=10；验证运行器使用 CPU 16、17，nice=10。
- 每个数据库通过 `systemd-run --user` 创建临时服务，`MemoryMax=8G`、`MemorySwapMax=0`、`TasksMax=256`。准备和验证进程在 4G 内存上限的用户 scope 中运行。
- 数据库轮流启停；验证结束或失败后停止项目服务。没有设置开机启动或修改用户 lingering。
- PostgreSQL 仅监听 `127.0.0.1:55432`；openGauss 仅监听本机 55433 和其内部端口 55434。Unix socket 位于权限 700 的项目状态目录。
- 数据、WAL、日志、软件包和运行库均保存在项目目录。没有修改全局动态库、APT 源、内核参数、防火墙或系统缓存。

CPU affinity 是本项目的使用范围，不是独占预留。其他用户仍可使用同一物理核；共享磁盘和缓存也没有隔离。上述措施限制影响范围，不能证明对其他任务零影响。当前未设置 I/O 限速。

## 版本与软件包

实际安装 PostgreSQL 14.24（Ubuntu 包版本 `14.24-0ubuntu0.22.04.1`）和 openGauss 6.0.1，正式报告须写这些实际版本，不能使用原 Docker 示例中的 PostgreSQL 18。

PostgreSQL 的 `postgresql-14`、`postgresql-client-14`、`libpq5`、`libpq-dev` 包通过 Ubuntu 已配置的镜像下载，只用 `dpkg-deb -x` 解压到 `runtime/postgres`，没有执行 `apt install`。

openGauss 使用官方 PPA 的 Ubuntu 22.04 amd64 包：

- URL：<https://ppa.launchpadcontent.net/opengauss/opengauss/ubuntu/pool/main/o/opengauss/opengauss_6.0.0~ubuntu22.04_amd64.deb>
- SHA-256：`954f1d790b0479fccfe60b64418cb4fb385830e729670ba1949e69a359ac90ed`
- deb 元数据版本为 `6.0.0~ubuntu22.04`，内部实际包含 `openGauss-Server-6.0.1-Ubuntu22.04-x86_64.tar.bz2`。以 `gaussdb --version` 和 SQL `version()` 为准。

先解压 deb，再解压内部 tar 到 `runtime/opengauss/usr/opengauss`，没有执行 deb 的系统安装脚本。包 SHA-256 和二进制版本保存在 `deploy/state/installation.json`、`*-version.txt` 中。

`scripts/configure_user_instances.py` 为已解压的上述包初始化独立数据库并编译客户端。它只支持新状态目录，避免覆盖已有实例。应在有内存限制的用户 scope 和明确 CPU affinity 下运行。

```bash
cd /data1/ycx/filmbench
systemd-run --user --scope --quiet \
  -p MemoryMax=4G -p MemorySwapMax=0 -p TasksMax=128 \
  taskset -c 8,9 nice -n 10 ionice -c 2 -n 7 \
  python3 scripts/configure_user_instances.py --db-cpus 8-15 --client-cpus 16,17
```

此初始化命令不用于当前已配置实例的重复安装。

## 兼容性修正

openGauss 默认的 A 兼容模式会把空字符串视为 NULL，而课程数据存在空姓氏，导致 `surname NOT NULL` 导入失败。因此实验实例使用 `gs_initdb --dbcompatibility=PG`，保留空字符串与 NULL 的区别。

openGauss 服务使用包内运行库；基准客户端使用系统 C++ 运行库加包内 libpq，解决主机编译器生成的程序需要较新 `GLIBCXX` 符号的问题。环境变量只在项目 wrapper 中设置。

- 初期失败记录保存在 `results/user-smoke*`。默认 A 模式的初始实例目录保存在 `deploy/state/opengauss-data-a-initial`，仅作为部署诊断备份。

下面是已执行的冒烟命令，重复运行时须更换输出目录：

```bash
source deploy/state/connections.sh
systemd-run --user --scope --quiet \
  -p MemoryMax=4G -p MemorySwapMax=0 -p TasksMax=128 \
  taskset -c 16,17 nice -n 10 \
  python3 scripts/run_suite.py \
    --config deploy/state/targets.json --manage-user-services \
    --out results/user-smoke-4 --scales 1 --repeats 1 \
    --point-requests 10 --clients 1 2 --concurrency-scales 1 --warmup 0 --duration 1 --load-repeats 1
```

独立正确性检查使用相同的用户 scope，运行 `python3 scripts/verify_user_instances.py --out results/user-correctness`。该脚本启动并轮流测试两套项目数据库，最后停止服务；输出目录也必须尚不存在。

`deploy/state/connections.sh` 权限为 600，状态目录权限为 700。不要提交这个目录或复制连接密码到报告。

原正式实验使用 `--profile compact` 精简方案，实际约 53 分 18 秒；s10/s100 输入及三档实验均已完成。历史冒烟命令补写了 `--concurrency-scales 1`，以便在新默认配置下复现原来的并发覆盖。
