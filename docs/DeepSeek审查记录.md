## 一、实质发现

1. **结论要看规模与指标。** 三档聚合 PG 均快于 OG（1× 5.771774 / 7.344759、10× 25.387403 / 44.411374、
   100× 234.024788 / 345.668623 ms）；三档人物连接 OG 均快于 PG（PG/OG = 1.444391/1.114076、
   1.347477/1.119667、1.419140/1.074425 ms）。原稿方向正确，需要补的是"限定 100×"与
   "连接三档输出行数相同"两点，而非修改结论。此前审查稿曾称聚合在更小规模不一致、连接在 100 倍反转，均为错误。
2. **点查的数字有前提。** 正式点查每轮 100 次、三轮同一随机序列，文件偏移索引的 100 次整批约 0.48 ms，
   另有索引建立 0.946 s；4.84 μs 是短批次、索引已装载的均值。正式表述应写明这一点，
   长批次与两种分布的补测命令见 `README.md`（五轮、每轮一个种子）。
3. **两条基线不同。** 原 compact 客户端绑定 CPU 16、17；补实验改用 24、25（或 24–27），
   原因是原处邻核有其他任务（`results/epyc-compact-evidence/run.json` 的 `client_prefix`、
   `docs/scaling-probe-protocol.txt`）。两批都称"8 核数据库 + 2 核客户端"，但不可拼接或配对比。
   图 2、图 3 共用补实验新基线；8+8 平衡组与 120 秒确认是各自独立的追加组。
4. **CPU 数字的口径。** `scaling-probe/scaling-analysis.json` 的 `cpu_method` 说明：核数是内部采样窗口内
   累计 CPU 时间增量的平均，与吞吐量窗口不完全重合，不是占用百分比或独占物理核；
   CPU 资源是 `taskset` 绑定范围，不是配额。
5. **数字应与数据摘要同源。** 正文尽量引用 `data.json` 的 `serial`、`point`、`search`、`cpu`、
   `interventions`、`mixed_metrics`、`long_ratio`、`balance` 等字段，避免手抄后与表格脱节。
6. **未测机制不要写成解释。** 只保留源码可查的预编译语句复用；不写"每次点查重复解析"之类推断。
7. **返回值口径。** 聚合输出组数每档不变，搜索返回记录随规模增长，更新返回受影响行数，
   三者与扫描工作量不是同一个量。

  使用本实验设置的数据库参数），一段讲文件与数据库的访问方式与功能选择；表格恢复四行两列。
  统计口径写清：点查为各轮平均单次耗时的三轮中位数，其余为三轮操作耗时的中位数。
- 点查限定语写到首页与第 02 节表注：每轮 100 次、同一序列、文件偏移索引整批 0.48 ms、
  不含索引建立与装载；第 03 节恢复 `d.serial` 原表，保留［最小值，最大值］。
- 第 02 节合并索引机制的重复解释并精简，使末段不再单独占页；图 1 注明"数据库索引连接耗时基本平坦"
  只适用于数据库侧，文件端连接随规模增长。

  图 3 表注改为"分别改变绑定 CPU 数，查询、数据与数据库设置相同"，不再声称所有条件相同。
- 第 05 节说明两批客户端绑定不同、只在本批内部比较；结尾说明构建在实验快照哈希不符或
