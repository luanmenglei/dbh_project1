## Ubuntu 编译与数据准备

需要 Python 3.9+、C++17、libpq 开发库；完整临时数据库测试还需 PostgreSQL 服务端工具。

```bash
sudo apt-get install build-essential libpq-dev postgresql python3 python3-venv numactl sysstat
make
python3 scripts/prepare.py --scales 1 10 100
```

已有数据目录不能覆盖；只生成缺少的规模即可。四表为 countries、movies、people、credits；后三张按关系复制并平移 ID，国家表保持 185 行。该扩容保持原字段分布，不代表独立新增真实数据。

单独编译提交的源码：

```bash
c++ -O3 -std=c++17 filmbench.cpp -I"$(pg_config --includedir)" \
  -L"$(pg_config --libdir)" -Wl,-rpath,"$(pg_config --libdir)" -lpq -pthread -o filmbench
```

默认 DDL 已内置，`--ddl sql/schema.sql` 可显式覆盖。数据仍需四个 COPY-text TSV；其来源、转义规则和生成脚本均保留在项目中。

### 从提交文件开始复现

仅有 `report.pdf` 与 `filmbench.cpp` 时，先获取配套课程数据和转换脚本。以下固定版本提供兼容的数据与脚本；将本次提交的 `filmbench.cpp` 放入克隆目录后编译。固定版本里的旧 `src/filmbench.cpp` 不包含本次索引完整性修复。

```bash
git clone https://github.com/luanmenglei/dbh_project1.git
cd dbh_project1
git checkout 668d1c787030c21b61bc062c55fca962ef4571d7
python3 scripts/prepare.py --scales 1
c++ -O3 -std=c++17 filmbench.cpp -I"$(pg_config --includedir)" \
  -L"$(pg_config --libdir)" -Wl,-rpath,"$(pg_config --libdir)" -lpq -pthread -o filmbench
./filmbench --backend file --op search_rows --data data/generated/s1 --keyword The
```

预期 `rows=1563`，表示匹配 1,563 部电影。若使用 `--op search_count`，程序返回一条计数结果的摘要，此时 `rows=1` 不表示只匹配一部电影。可将编译命令中的 `filmbench.cpp` 换为提交文件的绝对路径。

准备一个专用实验数据库后，将真实连接参数放入 `FILMBENCH_DSN`（不要提交密码）。默认 schema 为 `filmbench_s1`，第一次导入不加 `--reset`，遇到已有 schema 时程序拒绝覆盖：

```bash
./filmbench --backend postgres --op load --data data/generated/s1
./filmbench --backend postgres --op search_rows --data data/generated/s1 --keyword The
```

openGauss 需用其配套 libpq 重新编译，在相应连接环境下将后端改为 `opengauss`。上述小规模查询用于核对功能，不应拿本机测量与报告中的服务器数字拼成新的比较。

### 性能实验与提交源码的对应关系

- 当前提交版按六个命名空间整理，另在独立临时实例上通过文件、PostgreSQL、openGauss 的正确性回归，记录见 `results/review-namespace-20261018/`。这次调整不生成新的性能数字；构建程序通过 `docs/source-readability.json` 分别核对重组版验证与历史源码身份。
- 原主实验实际源码为 `experiments/baseline-20261012/src/filmbench.cpp`，同时保存在 `results/epyc-compact-evidence/source-snapshot/`。对应结果来自该快照，不能标为当前版本重新测得。
- 历史点查在准备阶段扫描 TSV 收集候选 ID，在执行阶段随机选 ID 并转成字符串；当前版本先生成完整请求序列，再开始查询计时。两版 `elapsed_s` 的边界存在差异，不能只按字段同名直接合并。
- 原始并发记录已分别保存 `read_p95_ms` 和 `write_p95_ms`。报告取“各轮 P95 的中位数”，不是把三轮请求合并后重新计算 P95。
- 120 秒 CPU 干预确认每个条件只有一轮；原三轮矩阵与单轮确认分别解释。文件索引构建耗时同样只有一次测量。

### 补测运行方法

长批次点查使用均匀、热点两种分布，每轮共享同一请求文件，轮间使用不同种子；三种后端核对内容摘要。以下命令用于新建实验，实际完成情况见对应结果目录。服务启动参数需设置实验的 CPU 与内存配置，不能直接复用先前正确性检查的两核配置。

```bash
python3 scripts/run_coverage.py --config deploy/state/targets.json --manage-user-services \
  --out results/new-point-performance --scale 100 --requests 100000 --repeats 5
python3 scripts/analyze_coverage.py results/new-point-performance
```

默认协议要求服务器满足负载和磁盘阈值。新版补测器在每个计时命令开始、结束及运行期间每秒采样，保存到该条记录的 `health` 字段；任一采样 load1>32、磁盘空闲≤40 GiB 或采样失败，该轮保留原始输出但标记 `measured=false`，并保存排除原因。下文的共享服务器协议另有准入条件。采样不保证 CPU 独占，也不能捕捉所有亚秒级干扰。`coverage.json` 保存合格轮数，只有全部轮次合格时整批 `performance_eligible=true`；审查器会从采样重新计算资格。报告保留原 100 次点查的结果及其短窗口局限；此前 `performance_eligible=false` 的正确性记录不改标为性能记录。

索引作用的单独验证在专用实验 schema 中进行：保持数据库、数据、人物编号和结果列不变，仅改变 `credits_person_idx` 是否存在，检查实际执行计划，分别预热、交替测量至少五轮，并核对结果摘要。原始源码允许用 `--ddl` 传入只删除这一条 `CREATE INDEX` 的建表文件，可通过重新导入建立两种状态；导入和索引建立不计入查询时间。

新脚本会自动交替两种索引状态，保存实际计划、数据指纹及逐轮负载。每对测量都合格才计算该对的加速比；正确性模式不生成性能加速比：

```bash
python3 scripts/run_index_ablation.py --config deploy/state/targets.json --manage-user-services \
  --out results/new-index-ablation --scale 100 --repeats 5
```

这些运行器会恢复专用 `filmbench_sN` 实验 schema，配置必须指向本项目的专用数据库。

### 2026-10-15 共享服务器补测协议

用户确认可以在其他任务仍运行时补测。本批使用数据库 CPU 9–16、客户端 CPU 24–25，仍在 NUMA 节点 0；改用 9–16 是为了避开 CPU 8 的活跃 SMT 兄弟核。数据库与客户端的内存上限仍为 8 GiB / 4 GiB。此批属于新的共享服务器对照，不能与历史不同 CPU 绑定、计时版本的记录拼接。

`--shared-host-reason` 显式启用第二版健康协议，必须同时指定 `--monitor-cpus`，将实验核及其 SMT 兄弟核的原始 CPU 计数存入逐轮采样。整机 load 继续保存，但不再按 32 排除；磁盘空闲需大于 40 GiB、可用内存至少 16 GiB，采样失败仍排除该轮。CPU 计数用于事后检查，**通过资格检查不代表 CPU 独占或没有共享缓存、内存带宽干扰**。不传该参数时仍使用原来的 load≤32 协议；旧记录的标记不变。

本批给两条补测命令追加以下参数，并使用配置中实际绑定 CPU 9–16 的数据库启动命令：

```bash
--shared-host-reason 'User authorized shared-host supplement on 2026-10-15' \
--monitor-cpus 9 10 11 12 13 14 15 16 24 25 73 74 75 76 77 78 79 80 88 89
```

长点查采用 100 倍数据、每轮十万请求、五轮、均匀与热点两种分布。人物索引对照也采用 100 倍数据和五轮，交替两库和有／无索引状态。每轮保留原始记录，不根据快慢挑选结果。

索引对照配置若为两库提供 `index_control` 命令数组，脚本会每库仅导入一次，再用 `manage_person_index.py` 事务性增删人物索引；初始和结束时核对四表摘要，每次测量前核对执行计划与连接结果。该命令需使用对应 SDK 的 libpq 与运行库环境，连接从指定环境变量读取。配置中没有控制命令时，仍采用重新导入两份 DDL 的通用方式。两种方式都将导入、索引切换和预热排除在查询计时之外。

本批已完成，原始证据分别为 `results/supplement-20261015-point/` 与 `results/supplement-20261015-index/`；协议、运行日志和审查摘要在 `results/supplement-20261015-metadata/`。90 项覆盖测量与 20 项索引对照全部通过，未排除任何轮次，两库实验前后四表摘要相同。人物索引的逐轮加速比中位数为 PG 243.3 倍、OG 566.9 倍，限于固定返回 54 行的查询。

采样窗口内整机 load1 范围为 29.91–120.99；数据库 CPU 16 的 SMT 兄弟核 CPU 80 平均忙碌约 46.0%，客户端兄弟核 88、89 也有活动。通过本批资格检查不意味着不存在竞争，不能将这些数字推广为独占环境性能。两套项目数据库已在运行结束后停止。

```bash

  --index results/supplement-20261015-index --out results/supplement-20261015-metadata/analysis.json
python3 tests/test_supplement_audit.py
```

## 数据库部署与连接

共享服务器使用普通用户私有实例，版本、资源边界与已完成的历史运行见 [用户目录部署](用户目录部署.md)。连接从 `POSTGRES_DSN`、`OPENGAUSS_DSN` 等命名环境变量读取，密码不写入报告或记录。

已经有用户目录 SDK 时，可只编译当前客户端，不重建数据库；输出必须为新目录：

```bash
python3 scripts/build_user_clients.py --runtime /path/to/runtime --out /path/to/new-build
```

openGauss 客户端需要匹配其认证协议的 libpq。将目标配置中 `binary` 指向对应 wrapper。

独立服务器也可使用原 Docker 路线：

```bash
python3 scripts/deploy_ubuntu.py --cpus 0-7 --mems 0 --memory 8g
python3 scripts/build_opengauss_client.py
source deploy/state/connections.sh
```

CPU 编号只是示例，按真实 NUMA/SMT 拓扑选择，并为客户端预留核心。部署脚本记录镜像摘要，拒绝覆盖既有部署；版本以实际 `version()` 为准。Docker 使用 `--manage-containers`，用户服务使用 `--manage-user-services`，二者互斥。运行器在成功、异常或中断退出时尝试停止两套受管后端，清理失败会标记 FAILED。

## 新版计时与扩展查询

`timing_version=2` 区分 `request_prepare_s`、`backend_setup_s`、`elapsed_s`；`setup_s` 为准备总量，索引构建独立记录。旧数据的 setup 含全表候选 ID 扫描，不能视为数据库本身初始化耗时，也不能从旧数字反推新分项。

当前文件索引使用 `FILMBENCH2`：包含完成标记、条目数与内容摘要，拒绝截断、重复条目、非法偏移及多余尾部数据。构建先写临时文件，完成同步后原子替换；失败保留原索引。旧 `FILMBENCH1` 索引需用当前程序重新执行 `--op build_index`。历史实验源码与原始数据继续保留原版本，新的完整性检查成本不反推到旧性能数字。

```bash
python3 scripts/prepare_requests.py --data data/generated/s10 --out results/new-requests \
  --requests 10000 --repeats 5
python3 scripts/run_coverage.py --config deploy/state/targets.json --manage-user-services \
  --out results/new-coverage --requests 10000 --repeats 5
python3 scripts/analyze_coverage.py results/new-coverage
```

共享请求序列包含均匀分布与 90% 请求落在前 1% ID 的热点分布。连接选择不存在、低、正关联数量的中间档和高关联人物；中间档按不同关联数量取中位，避免人数中位与低档都只返回一行。

默认补测要求启动时 load1≤32、磁盘空闲>40 GiB；负载不满足时停止。显式采用上文的共享服务器协议时记录负载、实验核及其 SMT 兄弟核活动，不再以整机 load 排除。显式增加 `--correctness-only` 可做功能验证，记录标记为非性能测量，不产生新的性能排名。

`--op functional` 验证非法外键被拒绝，以及“先更新、再失败、再回滚”恢复原值。补充运行还核对回滚后的四表指纹；这些证据不等同于隔离级别或崩溃恢复测试。

## 报告重建与证据审查

```bash
python3 -m pip install -r requirements-plots.txt
python3 scripts/build_typst_report.py
```

安装 Typst 0.14.2 或兼容版本并加入 PATH（也可传 `--typst /path/to/typst`）。上面的完整重建会审查历史及新版证据，生成 `report/data.json`、三个 SVG 图表、`output/pdf/report-typst.pdf`，并更新 `output/submission/report.pdf`、`filmbench.cpp` 和提交哈希清单。需要完整 `results/` 证据及 `results/review-index-health/verification.json`；不会用伪造数字补缺。

仅修改文稿时，无需 Python、数据库或原始实验目录，可直接使用已导出的数据和矢量图：

```bash
typst compile report/report.typ report.pdf
# 填写署名（默认留空）：
typst compile --input name=姓名 --input student-id=学号 report/report.typ report.pdf
```

使用 Windows 微软雅黑；其他系统安装静态版 `Noto Sans CJK SC`，通过 Typst 的 `--input 'font=Noto Sans CJK SC'` 或完整构建脚本的 `--font 'Noto Sans CJK SC'` 指定。等宽字体使用 Consolas（其他系统可替换为 DejaVu Sans Mono）。避免使用当前 Typst 尚未完整支持的可变字体。完整构建脚本也支持 `--name` 和 `--student-id`。历史 ReportLab 构建器 `build_final_report.py` 保留供追溯，不再作为当前报告入口。

审查使用显式异常，`python -O` 不会关闭检查；同时校验统计完整性和原始 stdout。历史哈希对应 `source-snapshot`，允许当前实现继续修正而不破坏旧证据。
